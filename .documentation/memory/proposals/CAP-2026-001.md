## Proposed Change

### Principle: I. Single Responsibility (amended)

> Each module MUST have one well-defined purpose. Business logic MUST be testable independently of infrastructure (GitHub Actions, CLI, caching). When a module does "too much," split it.
>
> **Size Guidance:**
>
> - Python modules and React components SHOULD stay under 500 lines of code (LOC).
> - Modules exceeding 500 LOC MUST carry an inline comment at the top explaining why the size is justified (e.g., large enum table, generated code, proven-stable utility).
> - Modules exceeding 800 LOC are presumed to violate single responsibility and MUST be split before additional feature work is merged — unless a Constitution Check in the plan explicitly justifies the exception.

**Rationale**: Four consecutive audits independently applied a 500-LOC heuristic that is not documented. Making this threshold explicit
(a) gives developers a clear, checkable signal, (b) makes the Constitution Test for "Single Responsibility" deterministic, and (c) reduces audit noise by removing the need for auditors to invent their own thresholds.

**MUST Requirements:**

- Modules ≥800 LOC must be split before new feature work merges (hard gate)
- Modules 500–799 LOC must include a top-of-file justification comment

**SHOULD Recommendations:**

- Keep modules < 500 LOC as a design target
- Use responsibility decomposition (fetcher → fetch_commits, fetch_security, fetch_pull_requests) rather than arbitrary file splits
- Review module size at plan phase, not post-implementation
